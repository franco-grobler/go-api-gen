go-api-gen

Introduction

A spec-first OpenAPI code generator for Go, built for microservices monorepos.

An alternative to oapi-codegen with one central idea: a shared schema is authored once, generated once, and imported by every service that uses it — while each service still gets a self-contained OpenAPI document for docs and gateways.

The problem

Generate Go from a bundled document and you cannot share a Go type.

Bundling is what a gateway and a docs portal need: redocly bundle walks every $ref and inlines it, so the output depends on no other file. But by the time a generator reads that document, the fact that User arrived from a shared file is gone. Each service gets a private type User struct, so billing’s User and identity’s User are distinct Go types with identical fields, and any code that spans both needs a conversion function.

oapi-codegen offers two ways around this. Both work; both charge for it.

  • import-mapping generates from the unbundled spec, where the external reference is still visible, and maps that document onto a Go import path. The keys are matched against the reference string exactly as written, so ../../pkg/schemas/openapi.yaml and ../../../../../pkg/schemas/openapi.yaml are two different keys for the same package. Every relative spelling in the tree needs its own entry, and the two consumers of the spec drift apart: documentation comes from the bundle, code from the source.
  • x-go-type travels inside the document and survives bundling, so the pipeline keeps its shape. But a shared package generated from its own annotated spec imports itself, which does not compile. The shared types have to be hand-written, and the schema stops being their source of truth.

Both are the same concession: sharing is bolted onto a pipeline whose only artefact is a bundle. go-api-gen makes ownership part of the model instead, and produces the bundle separately, for the readers that actually need one.

The model

Shared components live in a schema root, owned by no service. Each service’s spec lives beside the code that serves it and $refs into that root.

go-api-gen.yaml              at the repo root, beside go.mod
schema/
  user.yaml                  User, UserStatus, Address
  common.yaml                Money, PageInfo, shared parameters
services/
  billing/
    api.yaml                 the contract
    service.go               the handlers you write
    internal/api/            generated from it
  identity/
    api.yaml
    service.go
    internal/api/
gen/
  apitypes/                  the shared schemas, as one Go package
  openapi.yaml               the unified document

References are ordinary relative $refs, so the source tree stays legible to every other OpenAPI tool — redocly lint services/billing/api.yaml reads it unchanged:

payer:
  $ref: ../../schema/user.yaml#/components/schemas/User

Two outputs come out of each service, and they bundle differently on purpose. Billing’s generated Go imports the shared type:

import "github.com/acme/monorepo/gen/apitypes"

type Invoice struct {
	ID     uuid.UUID      `json:"id"`
	Payer  apitypes.User  `json:"payer"`      // one Go type across every service
	Total  apitypes.Money `json:"total"`
	Status InvoiceStatus  `json:"status"`
}

Billing’s openapi.yaml inlines it, because a gateway cannot follow a Go import. The document is self-contained and tree-shaken: shared schemas it reaches become components, shared parameters are inlined at their use sites, and shared schemas it never touches are left out entirely.

Ownership is checked rather than assumed. A schema reached by two services must live in a shared root, and a Go name claimed twice is an error that names both claimants.

Scalar types

Without a types entry, a scalar maps to the Go type you would write by hand:

OpenAPIGo
stringstring
string, format: date-timetime.Time: an RFC 3339 timestamp, 2026-10-27T09:30:00Z
string, format: datedate.Date, from the runtime module: an RFC 3339 full-date, 2026-10-27
string, format: byte or binary[]byte
integerint; int32 and int64 for those formats
numberfloat64; float32 for format: float
booleanbool

Any other format, time and uuid among them, is the base type until a types entry maps it.

A date is not a time.Time. A time.Time reads and writes a timestamp, so it would turn ?from=2026-10-27 away and answer with a time and a zone the contract never mentioned. date.Date reads exactly YYYY-MM-DD, rejecting a timestamp or a day the calendar does not have, and writes the same form back, in a parameter and in JSON alike. date.Of(t) and d.In(loc) convert to and from a time.Time. A team that already has a civil-date type can map the format to it instead:

types:
  format:date:
    go: civil.Date
    import: cloud.google.com/go/civil

A mapped type is decoded from a parameter through its UnmarshalText, and to and from JSON as encoding/json decides, so it needs encoding.TextUnmarshaler and should agree with its own JSON form.

Shared roots and services are keyed by name rather than listed, and the name is the one the tool uses everywhere else: in diagnostics (services.billing: rather than packages[2]:), and in unified.exclude, which names a service instead of repeating its output path. The Go package name is the basename of to — apitypes, api — overridable per entry with package:.

Targets are types, validate, server, client, fake, and spec. Naming one pulls in what it needs: server implies types, fake implies server. Relative paths resolve against the config file’s directory.

Loaded through Viper: YAML, JSON, or TOML, discovered by walking up from the working directory. Unknown keys are an error rather than a silent no-op. A few settings can be overridden from the environment with the GOAPIGEN_ prefix, for example GOAPIGEN_ERRORS_TYPE_BASE_URL — but generated code is committed, so an override that differs from what CI regenerates with will fail check.

Optional fields

Optional and nullable fields use Optional[T], which distinguishes the three states JSON actually has. A pointer can only express two of them, which is why pointer-based models cannot implement PATCH correctly.

type UpdateUser struct {
	Name  optional.Optional[string] `json:"name,omitzero"`
	Email optional.Optional[string] `json:"email,omitzero"`
}

req.Name.IsSet()    // was the key present at all?
req.Email.IsNull()  // present and explicitly null: clear the field
v, ok := req.Name.Get()

Unions

A oneOf or anyOf becomes a struct with one pointer field per member, of which exactly one is set:

Pet:
  oneOf:
    - $ref: '#/components/schemas/Cat'
    - $ref: '#/components/schemas/Dog'
  discriminator:
    propertyName: pet_type

// Pet is one of Cat or Dog: exactly one field is set.
type Pet struct {
	Cat *Cat
	Dog *Dog
}

switch {
case req.Body.Pet.Cat != nil:
	// ...
case req.Body.Pet.Dog != nil:
	// ...
}

return api.Pet{Dog: &dog}

A member that is a named schema gives the field its name. An inline member is named by its title, or else by the kind of value it holds: String, Integer, StringList, Object, and so on, with a number added if two would share a name.

Encoding writes whichever member is set. A union with no member set fails to encode, unless the union is nullable, in which case it encodes as null.

Choosing the member

Decoding a union means working out which member the JSON is, and how depends on whether the schema has a discriminator.

With a discriminator, the value of its property picks the member. Each member’s value comes from the first of these that applies:

  1. an entry in discriminator.mapping;
  2. the single value the member’s own discriminator property is fixed to, by enum or const. Many documents leave out the mapping and rely on this, rather than on the schema name the specification says to fall back to;
  3. the member’s schema name.

When two members end up with the same value, the discriminator cannot choose between them, and the union is decoded by shape instead.

Without a discriminator, the JSON is matched against the shape of each member. A member fits when:

  • the value is a JSON kind the member accepts;
  • for an enum or const, the value is one of those it allows;
  • for an object, every required key is present, no key is undeclared when additionalProperties is false, and every property restricted by enum or const (such as a type: {enum: [function]}) holds an allowed value.

When more than one member fits, the most specific wins: for an object, the member that declares the most of its keys, which is how Pydantic’s smart mode settles a union too. A tie is an error for oneOf. For anyOf, the first member in the tie wins.

Only the shape is used to choose. Once a member is chosen, its full validation runs as usual, and failures are reported inside the union’s location.

How this differs from JSON Schema

JSON Schema defines both keywords by full validation. A value is valid under oneOf when it passes every rule of exactly one member, and under anyOf when it passes at least one. A discriminator is only a hint for which member to check. The generated code departs from that in two ways:

  • It chooses by shape, not by every rule. Formats, lengths, bounds and nested properties play no part in the choice. Two members that differ only in those look the same, so a value can be decoded as the wrong one and fail that member’s validation, or be reported as union_ambiguous when only one member would accept it. Give such a union a discriminator, or a property fixed by enum or const in each member.
  • It accepts a oneOf value that fits more than one member, when one of them declares more of its keys. JSON Schema would reject the value. A Go value can only hold one member, and real documents, OpenAI’s among them, have oneOf members that overlap, so the more specific one is taken rather than the request refused.

A union whose members can be told apart by kind, required keys or a fixed property, which is most of them, is decided exactly as JSON Schema would decide it.

Errors

A value that is none of the members is not a decoding error: it is reported like any other validation failure, at the union’s location, with one of these types:

TypeWhen
union_tag_not_foundthe discriminator property is missing, or not a string
union_tag_invalidthe discriminator names no member
union_no_matchno member fits the value
union_ambiguousa oneOf value fits more than one member equally
 
{"type": "union_tag_invalid", "loc": ["body", "pet"],
 "msg": "Input tag 'bird' found using 'pet_type' does not match any of the expected tags: 'Dog', 'cat'",
 "ctx": {"discriminator": "'pet_type'", "tag": "bird", "expected_tags": "'Dog', 'cat'"}}

Null

A {type: 'null'} member makes the union nullable rather than adding a member. A union that is left with a single member is that member, so anyOf: [{$ref: User}, {type: 'null'}] is a nullable User: Optional[User] on a property. allOf: [{$ref: User}, {nullable: true}], the OpenAPI 3.0 way of writing the same thing, means the same.

Not supported yet

Each of these is rejected with an error naming the schema:

  • oneOf or anyOf beside properties or allOf. Move the shared properties into each member.
  • oneOf and anyOf on the same schema.
  • a union as an allOf member.
  • a union as a parameter.
  • an inline member of a discriminated union that has no discriminator value.

x-go-type on the union replaces all of this with a type of your own.

The unified spec

Each service gets its own document. The unified spec stitches them into one platform-wide document, for an API gateway, a docs portal, or a client that spans services. With unified.to set, build writes it with everything else, and check fails when it is missing or out of date, as it does for any other generated file:

$ go-api-gen build
  gen/apitypes/types.gen.go
  gen/openapi.yaml
  services/billing/internal/api/types.gen.go
  services/billing/internal/api/openapi.yaml
  services/identity/internal/api/openapi.yaml
go-api-gen: wrote 5 of 5 files

unify writes the same document on its own, and can put it elsewhere or pipe it to another tool:

$ go-api-gen unify --output dist/platform.yaml
go-api-gen: wrote dist/platform.yaml

$ go-api-gen unify --stdout | redocly lint -

Paths merge method by method, so two services may serve different methods of the same path — but the same one is a conflict, and so is a reused operationId. Both are refused with a message naming each contributing spec. Operations that declare no tags of their own are tagged with their service’s title, so a docs renderer groups the result by service rather than showing one flat list of every endpoint in the monorepo.

The HTTP layer

build generates the whole path from socket to handler: route registration on the stdlib ServeMux, parameter parsing, body decoding, and validation. A handler receives input that has already been checked.

type Handler interface {
	CreateInvoice(ctx context.Context, req CreateInvoiceRequest) (*Invoice, error)
}

srv := api.NewServer(myHandler, api.WithMiddleware(auth, logging))

The errors block of the config is already applied — NewServer seeds itself with it. To set something the config cannot state, start from that value rather than a fresh apierr.Options, since WithErrorOptions replaces the whole struct:

opts := api.DefaultErrorOptions()   // type_base_url, validation_title
opts.TraceID = tracing.FromRequest

srv := api.NewServer(myHandler,
	api.WithErrorOptions(opts),
	api.WithMiddleware(auth, logging),
)

Parameters

Path, query and header parameters are parsed into their declared types before the handler runs, and a value that does not parse is a 422 at the parameter’s own location, such as ["query", "from"], reported with every other failure in the request. Each type has its own failure:

Declared asAcceptsFailure

number4.2float_parsing
booleantrue, falsebool_parsing

A date is only a date: ?from=2026-10-27T00:00:00Z is a date_parsing failure, as is 2026-02-29. See scalar types.

Request bodies

A JSON request body is decoded into the request struct’s Body field and checked against its schema before the handler runs. A body is absent when it holds no bytes at all: a Content-Length of 0, or a chunked body that ends before its first byte. The length header alone cannot tell, so the generated code reads up to the first byte to find out (httpx.Body).

The request sendsrequired: truerequired: false (the default)
no body422, missing at ["body"]the handler runs, Body unset
bytes that are not JSON422, json_invalid at ["body"]the same
only whitespace422, json_invalid at ["body"]the same
JSON that breaks the schema422, each failure at its own locationthe same
nulldecoded as the zero value, then checkedBody set and null, not checked

A body of only whitespace is not absent: it is not JSON, so it is reported as such rather than quietly treated as missing.

An optional body is an optional.Optional, so a handler can tell a request sent without a body from one sent with an empty object:

type VoidInvoiceRequest struct {
	Path VoidInvoicePathParams
	// Body is unset when the request is sent without one.
	Body optional.Optional[VoidInvoice]
	Raw  *http.Request
}

func (s *Service) VoidInvoice(ctx context.Context, req api.VoidInvoiceRequest) (*api.Invoice, error) {
	if body, ok := req.Body.Get(); ok {
		// the client sent a body, and it passed validation
	}
	...
}

A required body is the schema’s type itself, since it is always there by the time the handler runs.

Handler docs

Each Handler method is documented with its operation’s summary and description, and one example request and response: what the handler is given, and what it should produce.

type Handler interface {
	// CreatePet: Create a pet.
	//
	// Example request (A dog):
	//
	//	{
	//	  "name": "Rex",
	//	  "kind": "dog"
	//	}
	CreatePet(ctx context.Context, req CreatePetRequest) (*Pet, error)
}

Examples come from the standard places first: example or examples on the JSON request body and the success response. A document that keeps them elsewhere can say where, as OpenAI’s does under x-oaiMeta:

examples:
  path: x-oaiMeta.examples   # from each operation, to one example or a list
  request: request.curl      # from each example; default "request"
  response: response         # default "response"
  title: title               # default "title"

Each value is a dot-separated path. Quote a segment that contains a dot, as in request."node.js", and use a number to index a list. A configured example fills in only the side the standard ones leave empty. An object, or a string holding JSON, is shown as indented JSON; a curl command contributes its -d body when that is JSON, and any other text is shown as written.

When a schema already has an operation’s <Op>Request name, as OpenAI’s CreateAssistantRequest does, the request struct is named <Op>Input instead.

Validation is generated Go, not tags read by reflection at runtime:

func (money Money) Validate(v *validate.V) {
	for _, name := range money.missingFields {
		v.Field(name).Fail("missing", "Field required")
	}
	if utf8.RuneCountInString(money.Currency) < 3 {
		v.Field("currency").Fail("string_too_short",
			"String should have at least 3 characters", "min_length", 3)
	}
}

Required fields get a generated UnmarshalJSON that records which keys the client actually sent, so an omitted field is reported as missing while a deliberate 0 or "" is not. A field that was never sent is reported once: its other constraints are skipped rather than measured against the zero value, so one absent input does not produce one error per keyword.

Custom rules

x-validate on a schema or property declares a rule you write in Go. The generator emits an interface and asserts the type satisfies it, so a rule named in the spec but never written is a compile error:

email:
  type: string
  x-validate: [corporate_domain]

// generated
type UserValidator interface {
	ValidateEmailCorporateDomain(v *validate.V)
}
var _ UserValidator = User{}

// yours, in a file the generator does not own
func (u User) ValidateEmailCorporateDomain(v *validate.V) {
	if !strings.HasSuffix(u.Email, "@acme.com") {
		v.Fail("corporate_domain", "Email must be on the acme.com domain")
	}
}

Rules are pure functions of the value. A check that needs a database belongs in the handler, using the same error builder so the response is identical:

if taken, _ := db.EmailTaken(ctx, req.Body.Email); taken {
	return nil, apierr.Validation().
		Field("body", "email").
		Fail("email_taken", "already registered")
}

Security

securitySchemes and security are read, and generate an Authenticator the server calls before any handler runs. The generator locates the credential where the specification says it lives; what a token means is not something a specification can say, so that part is yours.

security:
  - bearerAuth: []          # the document-wide default
paths:
  /login:
    post:
      security: []          # overrides it: this is how you get a token
components:
  securitySchemes:
    bearerAuth: { type: http, scheme: bearer }

// generated
type Authenticator interface {
	BearerAuth(ctx context.Context, r *http.Request, token string) (context.Context, error)
}

func NewServer(h Handler, a Authenticator, opts ...ServerOption) http.Handler

The authenticator is a parameter, not an option: a server that could be built without one would route requests nobody had checked. The context it returns is the one the handler receives, which is how the caller’s identity gets there — and the only way it does.

func (t *Tokens) BearerAuth(
	ctx context.Context, _ *http.Request, token string,
) (context.Context, error) {
	caller, ok := t.callers[token]
	if !ok {
		return nil, apierr.Unauthorized("this token is not recognised")
	}
	return context.WithValue(ctx, callerKey{}, caller), nil
}

Returning an error refuses the request; an *apierr.Problem is rendered as it stands, so a handler that wants 403 rather than 401 says so. A missing credential is a 401 carrying the WWW-Authenticate challenge RFC 9110 requires.

apiKey (header, query, or cookie), http (bearer, basic, or any registered scheme), oauth2, openIdConnect, and mutualTLS are supported. Several schemes in one requirement are an AND, several requirements an OR, and an empty requirement (- {}) admits a caller who presents nothing — one who presents a credential is still identified by it. oauth2 and openIdConnect methods receive the scopes the operation asked for.

Authentication is who the caller is; authorization is whether they may do this, and stays in the handler where the data is. See examples/microservices/identity.

Errors

Every failure — schema constraint, custom rule, or handler-raised — leaves in one RFC 9457 shape:

HTTP 422  application/problem+json
{
  "type": "https://errors.acme.io/validation_failed",
  "title": "Request validation failed",
  "status": 422,
  "detail": "2 fields failed validation",
  "instance": "/v1/invoices",
  "trace_id": "01J8X...",
  "errors": [
    {"type": "missing", "loc": ["body", "payer_id"], "msg": "Field required"},
    {"type": "string_too_long", "loc": ["body", "total", "currency"],
     "msg": "String should have at most 3 characters",
     "ctx": {"max_length": 3}}
  ]
}

An unexpected error becomes a 500 whose detail is withheld from the caller and logged instead, so a database message cannot leak through by accident.

A request body that cannot be decoded is reported at ["body"] itself: json_invalid when the bytes are not JSON, and missing when a body the operation requires was not sent at all. See request bodies for what counts as absent.

The runtime module

Generated code is thin. Everything that does not vary between services — the Optional[T] type, the validation accumulator, the error envelope and its middleware, and the server plumbing — lives in one module you install once:

$ go get github.com/franco-grobler/go-api-gen/runtime
PackageWhat it holds
runtime/optionalOptional[T]: absent / null / set
runtime/dateDate, a calendar day: what format: date decodes to
runtime/validateV, the field-error accumulator, and FieldError
runtime/unionChoosing a union’s member, by discriminator or by shape
runtime/apierrProblem, the error builders, and the middleware
runtime/httpxServer options, middleware ordering, response writing

It is a separate module from the generator, so depending on the generated code does not drag in the generator’s spec parser, Viper, or Cobra. It has no dependencies of its own.

The generator emits only what actually differs per service: the Handler interface, the request and response types, the routing table, and the decode path for each operation. A shared helper is never copied into a service — that would be the same duplication this tool exists to remove from schemas.

Commands

go-api-gen build     Generate every configured output
go-api-gen check     Report whether committed output is up to date (for CI)
go-api-gen unify     Stitch every service spec into one unified document

The CLI is built on Cobra, so go-api-gen completion <shell> produces a shell completion script.

build writes everything the config describes: each service’s code and document, each shared root’s package, and, when unified.to is set, the unified spec. A file whose content is unchanged is left alone.

Generated output is deterministic, so check is a reliable drift gate. It compares every file build would write, the unified spec included, and exits non-zero naming each one that is missing or differs.

unify writes the unified spec on its own: to unified.to, as build does, to another path with --output, or to standard output with --stdout.

Examples

All four examples are runnable programs, not snippets. Each has a binary under cmd/, a map behind a mutex standing in for the database, request logging through WithMiddleware, and a shutdown that drains in-flight requests.

The smallest is examples/petstore — one spec, one generated package, no shared schema root:

examples/petstore/
  go-api-gen.yaml
  api.yaml                the contract
  cmd/petstored/main.go   flags, logger, listener, shutdown
  service.go              the handlers you write
  store.go                the database: a map
  internal/api/           generated from api.yaml

$ cd examples/petstore && go run ./cmd/petstored
$ curl -s -X POST localhost:8080/pets \
    -H 'content-type: application/json' -d '{"name":"Fido","tag":"dog"}'
{"id":1,"name":"Fido","tag":"dog"}

examples/microservices is the other end: two services that are built and deployed separately, with the shared schema a third module they both require. type SendAt struct {

  • Type generation: structs, enums, allOf embedding, inline type synthesis, Optional[T], configurable format mapping
  • oneOf/anyOf as union types, chosen by discriminator or by shape
  • check drift gate
  • Generated validation from spec constraints, with required-field presence tracking
  • x-validate custom rules with compile-enforced interfaces
  • RFC 9457 error package and middleware
  • Server: routing, parameter parsing, body decoding, typed handlers
  • security: schemes, requirements, and a compile-enforced Authenticator
  • Named shared/services config, with targets implying their prerequisites
  • Selecting one service on the command line: go-api-gen build billing
  • Typed client
  • Test fakes

A union beside properties or allOf, a union as an allOf member or a parameter, and oneOf with anyOf on one schema are rejected with a clear error; see Unions.

Array and object parameters are read in the styles OpenAPI defines for them: form (exploded or not), spaceDelimited, pipeDelimited, and deepObject in the query, and simple in a path or header. An array of arrays or objects, an object with an array or object property, and the label and matrix path styles are rejected with a clear error.

One validation gap is silent — the constraint is accepted by the parser and never applied, so the generated server lets the value through. Do not rely on it until this says otherwise: multipleOf, uniqueItems, const, and additionalProperties: false, which does not reject unknown fields.

Contributing

Tools

Every tool the project uses is pinned in devbox.json, so a checkout builds the same way on any machine: Go, just, git-cliff, committed, mdBook, and pre-commit.

$ devbox shell        # a shell with every tool on PATH
$ just hooks          # once: install the commit-msg hook

Or run one command without entering the shell: devbox run -- just test.

The linter is the exception. golangci-lint refuses to lint code that targets a newer Go than it was built with, so just lint builds the pinned version from source with the toolchain go.mod selects, into .bin, and rebuilds it when either the pinned version or that toolchain changes. CI does the same.

Recipes

Recipes live in a justfile; just --list prints them.

$ just              # build, lint, test, and verify generated output
$ just test         # go test -race -shuffle=on, every module
$ just lint         # golangci-lint, the generator and the runtime
$ just generate     # regenerate every example
$ just tidy         # go mod tidy, every module, against its own requirements
$ just fix          # apply the linter's automatic fixes
$ just commits      # lint this branch's commit messages
$ just docs         # serve this book at localhost:3000

CI runs four jobs: build and test (-race -shuffle=on, with coverage), lint, module tidiness, and a generated-code gate that regenerates the examples, fails on any drift, and then compiles the result — because output that diffs clean but does not build would pass every other check. The test suite also generates a server from OpenAI’s published specification and compiles it; just update-openai-spec refreshes the copy in testdata.

Linting

Linting is strict. Hand-written code is held to 80 columns; generated files are excluded, since gofmt’s struct-tag alignment has no reason to respect a limit meant for human readers. Three exceptions are configured deliberately, each with its reason in .golangci.yml: govet’s shadow, staticcheck’s ST1005 (several diagnostics here are deliberately two sentences — the problem, then the fix), and gosec’s G304 (reading files the user names is what a generator does).

The linter version is pinned in justfile and .forgejo/workflows/ci.yml; keep them in step.

CI

The repository lives on a Forgejo instance, and GitHub holds a copy that Forgejo’s push mirror keeps up to date. Every pipeline runs on Forgejo Actions, from .forgejo/workflows; GitHub’s Actions are off. The jobs run in a pinned container — the Go image go.mod selects, or a Node image where no Go is needed — and install git-cliff, committed and mdBook from their release tarballs, checked against pinned checksums.

GitHub still shows what the pipelines make. The docs workflow publishes the book from main to the gh-pages branch, which the mirror copies to GitHub, where GitHub Pages serves it. The release workflow creates each release on GitHub as well as on Forgejo (see Releasing).

Commits

Every commit is a conventional commit, because the changelog is written from them:

fix(gen): a request struct yields its name to a schema that has it

Two tools check each message, in the commit-msg hook and again in CI:

  • committed checks its style, per committed.toml: an allowed type, a subject in lower case and at most 72 characters, body lines of at most 100 (wrap prose at 72; the limit is for quoted code and URLs), and no fixup! or WIP commits.
  • git-cliff checks that the changelog can file it, per cliff.toml. It is stricter about a type’s spelling, and a commit it cannot file would fail the release.

The allowed types are feat, fix, perf and revert, which reach the changelog, and build, chore, ci, docs, refactor, style and test, which do not. A ! after the type, or a BREAKING CHANGE: footer, marks a breaking change. The two configuration files list the types separately; keep them in step.

A pull request is merged with a merge commit or rebased, never squashed, so each of its commits reaches main and the changelog. A merge commit is titled <pull request title> (#<number>), so CI holds the title, with that suffix, to the same rules; the changelog leaves merge commits out, since the commits they merge are listed already.

Layout

cmd/go-api-gen/          the CLI
internal/                config, spec loading, ownership, emitters
runtime/                 a separate module: what your services import
examples/petstore/       one service, no shared root
examples/unions/         one service whose contract is oneOf unions
examples/monorepo/       two services in one module, sharing a schema root
examples/microservices/  the same two, as three separately built modules
docs/                    this book
testdata/openai/         OpenAI's specification, a real-world test case

Each example carries the specs, the generated code, and the handlers you would write, and all four are built and tested in CI.

Releasing

The generator and the runtime module are released together, under one version. A release is a pair of tags on one commit, vX.Y.Z for the generator and runtime/vX.Y.Z for the runtime, since runtime/ is a module of its own and Go finds its versions under tags prefixed with its directory. Go needs nothing more: the module proxy serves a version straight from its tag.

The version

git-cliff works the version out from the commits since the last release, by the [bump] rules in cliff.toml:

Since the last releaseBefore 1.0.0From 1.0.0
a breaking changeminormajor
a featminorminor
anything elsepatchpatch

The first release is v0.1.0. Leaving 0.x is a deliberate choice, made by asking for v1.0.0 explicitly.

Preview what a release would say, without making one:

$ just release-notes          # the next entry, version worked out
$ just release-notes minor    # as a minor release

Cutting a release

$ just release                # version from the commits
$ just release minor          # or patch, major, or an exact v1.0.0-rc.1

This starts the Prepare release workflow on main, which:

  1. runs CI on the commit;
  2. has git-cliff work out the version and add its entry to CHANGELOG.md;
  3. commits that as chore(release): vX.Y.Z and tags it with both tags;
  4. pushes the commit and both tags in one atomic push, so if main moved meanwhile, nothing is half released.

The tags start the Release workflow, which checks they are a pair on one commit on main, runs CI against it, and publishes the release with that version’s changelog entry as its notes: on Forgejo, then on GitHub, once Forgejo’s push mirror has brought the tags there. Last, it warms the Go module proxy, which reads the version from GitHub.

Both workflows run on Forgejo (.forgejo/workflows); just release starts the first with fj, or run Prepare release from the repository’s Actions tab.

Two secrets, both set by the infrastructure that makes the repository:

  • RELEASE_TOKEN pushes the commit and tags, because a push made with the workflow’s own token starts no workflows: the tags would land and nothing would publish them. It is a Forgejo access token with the write:repository scope, of a user that may write to this repository alone and push to main past its branch protection.
  • GH_APP_PRIVATE_KEY, with the variable GH_APP_ID, creates the GitHub release as a GitHub App with read and write access to contents. Each run makes a token from them that lasts an hour and reaches this repository alone. GitHub’s copy takes tags only from the mirror, so the workflow adds the release to a tag already there.

The changelog

CHANGELOG.md is written by git-cliff from the commit messages, never by hand; to change how it reads, edit cliff.toml. feat, fix, perf and revert commits are listed, grouped, with breaking changes first. The other types are left out, as work that changes nothing for a user of the generator or the runtime.
